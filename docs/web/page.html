What reaches the model

A coding agent works only from what fits in its context. On real issues, from repositories the methods never saw, this measures how much of the code each fix needed actually reaches the model, at 8,000, 32,000 and 128,000 tokens, and what changes that.

What is measured

Each issue comes from ContextBench, with the lines of code annotators judged necessary to resolve it. A method is given the issue's text and the repository at that commit, and returns files in order. They are kept, in that order, while they fit the budget. The fix itself is never shown.

Recall is the share of the needed files that were kept. If an issue needs four files and a method's selection holds three of them within 32,000 tokens, its recall at 32k is 0.75. Recall alone is easy to game: return everything, and a large enough budget scores 1.0. So precision sits beside it, the share of kept files that were needed. The ceiling is the needed files themselves: below 1.0 whenever they do not fit.

Methods were tuned on 281 issues from 40 repositories. Everything on this page, unless marked otherwise, is from further issues from other repositories, held out until the methods were fixed and run once.

Lexical ranking: three things a word count misses

BM25 scores a file by the words it shares with the issue. But issues are not search queries. They name files outright, quote identifiers in backticks, and describe behaviour that tests and documentation also describe. Three signals were added: a file the issue names comes first; a file that defines a named identifier is lifted above files that merely use it; and tests, examples and prose rank below code.

On the held-out issues they take recall at 32,000 tokens from to , for no cost at run time. This is the default for repo2txt select. Its weakness is precision: it fills whatever budget it is given.

Why the model first stopped at three files

The first model selector showed Claude Haiku 5.5 the directory tree with token counts and let it choose. It named a median of three files, used 14,000 of 32,000 tokens, and stopped. Of the 233 needed files it missed on the tuning issues, a third were in the lexical ranker's top 30, which the model never saw. Seeing a file in the tree barely helped: it found 43% of the needed files shown to it and 39% of those hidden in collapsed directories.

Two changes fixed most of this. The model was shown the ranker's top 30 beside the request, and the prompt was rewritten to say why completeness matters: whoever reads the selection works from those files alone, so a file they need and were not given stops them, while a file they did not need costs only its tokens.

The tool that looked useless

Every trained code-search agent published this year searches and reads. So two tools were added: a pattern search over file contents, and an outline of what a file defines. Recall fell by six points. Before recording that, ten of the transcripts where it fell were read.

Every “no match” in the failing run was reported without the file being read: the search tool treated a file path as a directory and looked inside it for files. The files did contain the terms, and three of them were the files the fix needed. The model kept searching until its rounds ran out, then wrote that it had selected six files. It had selected none.

With the search fixed and a round kept for selecting, the tools recovered and then tied the kept selector at one and a half times the cost, probably because the shortlist already does a search's work before the model starts. They were removed. Had the transcripts not been read, this would have been recorded as “tools do not help”.

Lines, not files

At 8,000 tokens even a perfect choice of files reaches only part of what is needed, because the needed files often do not fit whole. But the needed lines themselves total about 2,000 tokens. Choosing lines instead of files could almost close that gap, if the right lines can be found.

Finding them by the issue's words failed: the lines a fix needs often do not contain those words, and focused views dropped them. What worked was asking the model again. It first chooses files at four times the budget, then sees outlines of those files, every block with its line range and size, and picks the ranges to read. The rest of the budget goes to its chosen files whole.

What could overturn this

Python. Half the tuning issues were Python, and the ranker's signals recognise a fixed list of declaration keywords. The held-out set is more mixed, and the gap between Python and the rest is the first place to look for a signal fitted to its training data.

One run, one model. Each configuration was run once with one small model. How much its choices vary from run to run, and whether a stronger model chooses better, were not measured.

Memory of the fix. Whether the model had seen these repositories and their fixes in training was not measured. The lexical rows are unaffected; the model rows could be.

What “needed” means. The needed files are sufficient, not minimal, so precision is understated. And the earliest twenty-issue pilot, run before the split existed, included issues from four repositories that were later held out; no tuning decision was made on it.
