Findings

  • A small model beats the lexical default, on work it had never seen. At 32,000 tokens the model selector delivers of the needed files against for the default, issues better and worse. The test was written down before the run, and held for all three models tried.
  • The smallest model is the right one. Claude Haiku 5.5 matches DeepSeek and beats Claude Sonnet 5.5 on recall, at a sixth and a fourteenth of their cost. Sonnet picks fewer files, more of them needed, and misses more.

What is measured

Each issue comes from ContextBench, a 2026 benchmark of real GitHub issues in eight languages, with the lines of code annotators judged necessary to resolve it. A method is given the issue's text and the repository at that commit, and returns files in order. They are kept, in that order, while they fit the budget. The fix itself is never shown.

Recall is the share of the needed files that were kept. If an issue needs four files and a method's selection holds three of them within 32,000 tokens, its recall at 32k is 0.75. Recall alone is easy to game: return everything, and a large enough budget scores 1.0. So precision sits beside it, the share of kept files that were needed. The ceiling is the needed files themselves: below 1.0 whenever they do not fit. Line recall, used where line ranges come in, is the share of the needed lines delivered; a whole file delivers all of its lines. Both are averaged per issue, and an issue where nothing is delivered scores 0.

What “needed” means is not settled, so three definitions are scored. Annotated, the default here: the code people traced from the fix and checked was enough for a model to write one. Edited: the lines the fix itself changed. Explored: the lines that successful agents read, from SWE-Explore, for a minority of issues. They disagree. A perfect choice of the annotated files delivers of the edited files and of the explored ones; a perfect choice of the edited files, of the annotated ones. The order of the methods below is the same under all three.

The methods were tuned on other issues. Everything on this page, unless marked otherwise, is from issues from repositories that no method had been run on, run once after the configuration was frozen and the tests written down.

Which model

The same selector was run with three models, each through its provider's own API with prompt caching on and effort set explicitly. Bigger or more deliberate did not help: Haiku matched DeepSeek and beat Sonnet. Sonnet is the most precise and the least complete, a lean it shows on every benchmark here; DeepSeek takes more rounds and writes several times the output.

On another benchmark

Agent Retrieval Bench asks for the files a coding agent needs next, from a failing trace, a review comment, a pull request's intent or one edited file. Its samples, corpus and evaluator were used unmodified. Nothing here was tuned on it. Its headline measure, budgeted context yield, is the share of needed files that reach an 8,000-token context packed in ranked order.

Lexical ranking: three things a word count misses

BM25 scores a file by the words it shares with the issue. But issues are not search queries. They name files outright, quote identifiers in backticks, and describe behaviour that tests and documentation also describe. Three signals were added: a file the issue names comes first; a file that defines a named identifier is lifted above files that merely use it; and tests, examples and prose rank below code.

On the fresh held-out issues they take recall at 32,000 tokens from to , for no cost at run time. This is the default for repo2txt select. Its weakness is precision: it fills whatever budget it is given.

Why the model first stopped at three files

The first model selector showed Claude Haiku 5.5 the directory tree with token counts and let it choose. It named a median of three files, used 14,000 of 32,000 tokens, and stopped. Of the 233 needed files it missed on the tuning issues, a third were in the lexical ranker's top 30, which the model never saw. Seeing a file in the tree barely helped: it found 43% of the needed files shown to it and 39% of those hidden in collapsed directories.

Two changes fixed most of this. The model was shown the ranker's top 30 beside the request, and the prompt was rewritten to give it the reason for completeness. Its key sentence:

Whoever reads your selection works from those files alone. A file they need and were not given stops them; a file they did not need costs only its tokens. So lean towards including.

With both, the median selection doubled to six files.

The tool that looked useless

Recent trained code-search agents, such as Cognition's SWE-grep and Chroma's Context-1, work by searching and reading. So two tools were added: a pattern search over file contents, and an outline of what a file defines. On the tuning issues, recall fell by six points. Before recording that, ten of the transcripts where it fell were read.

Every “no match” in the failing run was reported without the file being read: the search tool treated a file path as a directory and looked inside it for files. The files did contain the terms, and both files it reported this way were files the fix needed. The fault first shows in round 2. The model kept searching until its rounds ran out, then wrote that it had selected six files. It had selected none.

With the search fixed and a round kept for selecting, the tools recovered five points and then tied the kept selector (−0.01, −0.05 to +0.02) at one and a half times the cost, probably because the shortlist already does a search's work before the model starts. They were removed. Had the transcripts not been read, this would have been recorded as “tools do not help”.

Lines, not files

At 8,000 tokens even a perfect choice of files reaches only part of what is needed, because the needed files often do not fit whole. But the needed lines themselves total about 2,000 tokens. Choosing lines instead of files could almost close that gap, if the right lines can be found.

Finding them by the issue's words failed: the lines a fix needs often do not contain those words, and focused views dropped them. What worked was asking the model again. It first chooses files at four times the budget, then sees outlines of those files, every block with its line range and size, and picks the ranges to read. The rest of the budget goes to its chosen files whole.

What could overturn this

Memory of the fix. Whether the models had seen these repositories and their fixes in training was not measured. The lexical rows are unaffected; the model rows could be.

Few repositories. The fresh set has repositories, and a handful carry many of its issues; intervals are wide, and leaving out any one repository moves the main differences by at most 0.02.

One run each. Four repeat runs elsewhere moved the model selector's mean recall by 0.003, so one run settles an average. A quarter of single issues changed between those runs, so the example at the top is one draw; it was chosen because all three models agreed on it.

What “needed” means. Each definition is one sufficient set, not the only one, so precision is probably understated. No test of whether a model can fix the issue from what was delivered was run.

The cost of caching. Keeping each request's opening stable, which is what makes prompt caching work, may still cost about two points of recall on the tuning issues; the interval includes zero.

Conclusion

Three things transfer beyond this tool. A model asked to choose context should be told what a miss costs, because left to itself it stops at the obvious files. The smallest capable model is the one to measure first: here it was also the best. And a harness should be judged from transcripts and checked against known answers as well as scored: a wiring bug, a mis-scored metric and an adapter that misused a baseline all looked like results until they were read.

Methods in brief

Data: ContextBench at a pinned revision; the fresh held-out set is the full release's issues outside its verified subset, on the held-out side of a split by repository, run once. Models: Claude Haiku 5.5 and Sonnet 5.5 at medium effort, DeepSeek flash at high (its lowest honoured level), each through its provider's own API with prompt caching, one run per configuration. Haiku at 128,000 tokens was added after the pre-registered runs. Budgets are counted in o200k_base tokens; each provider's tokeniser differs. Intervals: 95%, 4,000 bootstrap resamples of whole repositories. The harness checks oracles, budgets and reproducibility before any number is reported. The full report and the pre-registration are in the repository.

Reproduce it

uv sync --group bench python -m bench.check --tasks 12 python -m bench.run --split test --unseal --subset fresh --tasks 300 \ --methods smallest,bm25-plain,bm25,oracle:annotated --out fresh.jsonl BENCH_MODEL=haiku BENCH_CLIENT=client.py python -m bench.run --split test --unseal \ --subset fresh --tasks 300 --methods llm --budgets 8k,32k --out fresh-llm.jsonl python -m bench.report fresh.jsonl
